# 翻訳コア

更新日：2026-11-10

モデルの読み込みと生成（`offscreen/`）、何をどうまとめて訳すか（`core/translator.js`）、キャッシュ（`core/cache.js`）、未使用時の解放（`background/idle.js`）。

## 方針

- Android アプリの翻訳コア（`Pfml3PromptBuilder.kt`・`BatchTranslator.kt`）と同じプロンプトと、同じまとめ訳しの考え方を使う。
- モデルはOffscreen Documentに1つだけ読み込み、ページ・テキスト翻訳・選択範囲で共有する。
- 遅さを隠さず、待ちの理由を測れるようにする（調査用のログ）。

## モデルと読み込み

- 取得元は Hugging Face のコミットに固定した URL（`offscreen/offscreen.js` の `MODELS`）。配布元は 2026-11-06〜08 にチャットテンプレートだけを何度も更新しており、`main` から取ると中身が変わる。この拡張機能はチャットテンプレートを使わないので、テンプレートの違いは訳に影響しない。
- 初回だけ取得し、wllama が OPFS に保存する（`useCache: true`）。進み具合は `local-progress` でService Workerへ送り、訳しているページのバー（無ければ右下）に出す。
- 読み込みの設定：スロット数（`n_parallel`）は「同時に訳す同時実行数」＋1（既定4＋1＝5）、1スロット4096トークン（`n_ctx` は 4096×スロット数）、`n_ubatch` は設定の値（既定512）、`n_batch` は 2048 と `n_ubatch` の大きい方、`swa_full: true`（下の「判断の記録」）。
- 別のモデル・動作モード・調整値へ切り替えるときは、前のモデルを `exit()` してメモリーを空けてから読み込む。

### 同時実行数の切り替えとメモリー

既定の同時実行数は `shared/settings.js` の `DEFAULT_PARALLEL`（現在8）で決める。`LOCAL_DEFAULTS`、設定の補正、ページ側のキュー、offscreen の省略時の値、自動調整の基準がこの値を参照する。保存済みの `chrome.storage.local.parallel` はそのPCの選択として引き継ぐため、定数の変更は既定で動いているPCに効く。

| 設定から導く値 | 同時4本 | 同時8本 |
| --- | ---: | ---: |
| モデルのスロット数（`parallel + 1`） | 5 | 9 |
| `n_ctx`（4096×スロット数） | 20480 | 36864 |
| `n_ubatch` の既定 | 512 | 512 |
| `n_batch` の既定 | 2048 | 2048 |

1本あたりの文脈長を保つため、8本では全体の文脈長も増やす。`swa_full: true` により SWA の KV も全長で確保するので、同じモデル・KV型なら KV の容量は文脈長の比で約1.8倍になる（設定値からの見積もり）。モデルの重みは共有され、スロット数に比例して複製されるのは KV などの実行用メモリー。

GPU で設定の同時実行数を読み込めないときは、すぐ CPU へ落とさず、4本・1本と下げて GPU で読み込み直す（段階的な降格、`offscreen.js` の `degradeSteps`。sakutto の 16→4→1→CPU と同じ考え方）。失敗した読み込みは `exit()` で GPU メモリーを空けてから次を試す。GPU の1本でも CPU より約2〜7倍速い（「動作モード」）。1本でも読めなければ、自動モードは CPU で読み込み直し、GPU を明示した設定はエラーを返す。下げて読み込んだときも、ページは設定の同時実行数で送ってくるので、offscreen の `acquire` が同時に計算させるリクエストを読み込めたスロット数までに抑え、あふれた分を順番に待たせる。待つ間に取り消されたリクエストは生成しない。状態（`model-status`）の `parallel` は実際に読み込めた同時実行数を返す。

ubatch は1回の計算へ渡す上限で、8本全部の原文が収まる必要はない。超えた原文は分けて処理でき、`n_batch >= n_ubatch` の関係も保つ。8本の採用実測も ubatch 512 なので、同時実行数と同時に ubatch を上げる変更は加えない。

ページは `page/queue.js` が設定の同時実行数まで送る。テキスト翻訳の `translateLines` は全バッチを `Promise.all` で送り、モデル側で順番待ちにする。複数のページやテキスト翻訳が重なると、追加した1スロットを選択範囲へ専用に予約する保証はない。テキスト翻訳の送信も設定の同時実行数にそろえる案は、バッチを共有キューへ入れて `parallel` 個の worker から順に送る方法。これは送信方式の変更として提案中で、今回の既定値集約には含めていない。

### offscreen の翻訳要求

ページの `translateBatch`、選択範囲の `translateText`、テキスト翻訳の `translateLines` は、いずれも `core/engine.js` の `complete` → offscreen の `complete` → wllama の `createCompletion` を使う。この生成経路は翻訳専用で温度0に固定し、次を渡す。

```javascript
backend_sampling: true,
backend_sampling_token_only: true,
samplers: ['temperature'],
```

`backend_sampling` は GPU で token を選び、sampling パッチの token-only は条件を満たすときだけ選んだ token ID を返す。`samplers` を temperature だけにすることで、温度0でも残っていた top-k/top-p の並べ替えを省く。CPU では自前パッチの既存 sampling 経路へ戻る。逐次受け取り、使用量、停止文字列、打ち切り、取り消しは既存の仕組みを使う。

配布版3.13.0でも `backend_sampling` と `samplers` は受け取る。`backend_sampling_token_only` は自前パッチで追加した項目で、配布版では未知の項目として無視される。wllama の JS は追加項目を completion の JSON へ渡し、固定版の [server-schema.cpp](https://github.com/ggml-org/llama.cpp/blob/7d7f0287530bc8981690f361d8c1627dbae1c99a/tools/server/server-schema.cpp) は登録した項目だけを評価する。token-only の読み戻し削減と argmax の同点規則をそろえる効果には、採用した sampling パッチを含む WASM が必要。

## 動作モード

| 設定 | 動き |
| --- | --- |
| 自動（既定） | GPU（`n_gpu_layers: 99`）で読み込む。推論エンジンが GPU を使えないと報告したら CPU として使う。GPU で読み込めなければ同時実行数を4本・1本と下げて試し、それでもだめなら CPU で読み込み直す。GPU の計算が止まったら CPU で読み込み直して訳し直す（下記） |
| GPU | WebGPU で動かす。GPU を使えない・計算が止まったときは CPU へ切り替えず、エラーを返す |
| CPU | `n_gpu_layers: 0` で WASM。スレッド数は既定で論理コアの半分（wllama の既定と同じ。残りを画面の処理に空ける） |

CPU のマルチスレッドには SharedArrayBuffer が要るので、manifest の COOP/COEP で拡張機能のページを分離している（Offscreen Documentで `crossOriginIsolated` が true になる）。動作モード・スレッド数を変えると、Service WorkerがOffscreen Documentを閉じ、次の翻訳で新しい設定で読み込む。

### GPU の選択と、使えない・止まったときの扱い

GPU を選び、デバイスを取り、正しく計算できるかを確かめるのは推論エンジン（wllama の中の ggml-webgpu）だけにする。パッチは `tools/wllama/patches/adapter`（sakutto 0007 の移植と報告の追加）。拡張機能は GPU を自分で求めず、推論エンジンが起動時に出す1行の報告（`ggml_webgpu: report {JSON}`）を `offscreen/gpu.js` で読み、表示と調査用のログに使う。画面に出す GPU と推論に使う GPU がずれないようにするため。WebGPU のアダプターはワーカーへ渡せないので、拡張機能の側で選んで渡す形は取れない。

| 段 | 推論エンジンがすること | 報告に残るもの |
| --- | --- | --- |
| アダプター | `powerPreference` を high-performance・既定・low-power の3通りで求め、この順で shader-f16 を持つ最初のものを使う | 3通りそれぞれの名前・ベンダー・ID・shader-f16・subgroups の大きさ。どれを使ったか |
| デバイス | アダプターの上限 → 2 GiB - 4 に抑えた上限→ 既定の上限 → shader-f16 だけ、の順に求める。上限だけ下げる段では subgroups を外さない | 取れた段 |
| 検算 | workgroup の足し算（答え136）が合わなければ GPU を使わない。subgroups を使うときは実際の subgroup_size を読み、報告された範囲に無ければ subgroups を切る。大きさが分からないときも推測せず切る | 足し算の答え、subgroup_size、切った理由 |

どれかで失敗すると GPU の数を0として登録し、モデルは CPU に載る。報告の `ready` が false なら、自動のモードはそのまま CPU として使い、GPU を明示したモードはエラーを返す。

Windows の Chrome 系のブラウザーは `powerPreference` を採らない（crbug 369219127。1.1.8（試験版）では、外付けGPUのノートPCで high-performance を求めても内蔵GPUが返った）。報告の3通りが同じ GPU なら、ブラウザーが GPU を1つしか見せていない。Chrome は複数の GPU を同時には使わず、ブラウザーが使う GPU はブラウザーの外で決まる。拡張機能から変える手段は無いので、利用者が変える手段を設定画面で案内し、その場所を開くボタンを置く：Windows の設定（システム → ディスプレイ → グラフィックス）でブラウザーに「高パフォーマンス」か使う GPU を選ぶ（`ms-settings:display-advancedgraphics`。ブラウザーの確認の後に開く）、または `brave://flags/#force-high-performance-gpu`（Chrome・Edge はそれぞれの flags）を有効にする。どちらもブラウザーの再起動の後に効く。今の GPU が内蔵か単体かは、ブラウザーが出す名前（ベンダー・アーキテクチャ）から正しく判定できないので、判定せず、案内はいつも出しておく。Windows の設定を書き換える補助プログラムは作らない（Windows の設定画面と同じことをするだけで、インストールと権限が増えるため。2026-11-25、作者の判断）。

計算中に推論エンジンが止まったとき（WebGPU の検証エラーなどで WASM ごと止まる。`(ABORT)`・`wllama has crashed`）は、そのモデルを外す。自動のモードでは、Offscreen Documentを閉じるまで GPU を使わず、CPU で読み込み直して同じリクエストを1回だけ訳し直す。同じ GPU で読み込み直しても同じ所で止まるため。閉じた後（未使用が続いたとき・「モデルを解放」）の次の読み込みでは、GPU をもう一度試す。

**使う GPU を確かめる**：設定画面を開いたときと「確かめ直す」で、使う GPU を確かめて出す（`gpu-check`）。モデルを読み込み済みなら、そのモデルを読み込んだときの報告を出す。読み込んでいなければ、モデルなしで推論エンジンを起動して報告を受け取る（wllama にパッチで足した `probeBackend`。GPU の登録は起動時の `llama_backend_init` で行われるので、モデルは要らない。数秒で、何も取得しない）。読み込みと同じ起動の処理で確かめるので、GPU を別の方法で求めない。インストール直後も、ブラウザーの GPU を変えて再起動した後も、開けばすぐ分かる。前回の結果を使い回さない。

利用者向けの文は `shared/gpu.js` だけで作る（GPU の名前、使えない理由、いつ・どう確かめたか、ブラウザーが見せている GPU の数）。上部の状態とボタンのメニューの GPU 名も、同じ報告から出す。

調査用のログには、読み込みごとの報告の要約（`GPU`・`GPU読み込み失敗`）、止まったときの理由（`GPU失敗`）、確かめた結果（`GPUの確認`）を、推論エンジンの警告・エラーの最後の数行とともに残す。推論エンジンのログは、起動時の報告のほかは警告・エラーだけを受け取る（`log_level: WARN`）。

## PCに合わせる調整

動作モード・スレッド数・同時に訳す同時実行数（`parallel`）・ubatch は、PCの性能で合う値が違う（検証環境Bは内蔵の Radeon 860M、検証環境Aは単体の RTX 4060）。そのため `chrome.storage.local` に置き、Brave の同期で他のPCへ渡さない（設定の版4で sync から移した）。値は `shared/settings.js` の `LOCAL_DEFAULTS` と選択肢、読み出しは `background/config.js`。

| 項目 | 効くところ | 既定 |
| --- | --- | --- |
| 同時に訳す同時実行数 | ページ側の同時送信数（`page/queue.js`）と、モデルのスロット数（＋1）。選択肢は1・2・3・4・6・8・16本 | 8 |
| ubatch | 原文の読み込みで GPU へ一度に渡すトークン数（`n_ubatch`） | 512 |
| スレッド数 | CPU で動かすときの WASM のスレッド数 | 自動（論理コアの半分） |

設定画面の「このPCに合わせる」（`background/tune.js`）は、ページの翻訳と同じ形のバッチ（4行・約230字）24個を、設定を変えて読み込み直したモデルで訳し、24個を訳し終えるまでの時間を比べて、いちばん速い設定を保存する。訳文のキャッシュ（`core/cache.js`）は通さず、モデルのキャッシュ（読み込み済みの原文、`cache_prompt`）も切る（`noCache`）。

- 2026-11-10 に測り方を直した（作者の依頼）。以前は8バッチをキャッシュありで繰り返し訳していた。(1) 2回目以降は同じ原文の読み込みがキャッシュで省かれ、実際のページより速く出ていた（検証環境Bの同時8本で、キャッシュあり2.3秒・キャッシュなし3.9秒）。(2) 8バッチだと8本だけが1巡で終わり、3本・6本は端数の巡で不利になる。24バッチは2・3・4・6・8本のどれでも割り切れる。24バッチは `SAMPLE` の行を組み替えて作り、すべて別の文。直した後の検証環境Bは、8本 12.9秒・6本 12.7秒・3本 17.3秒・2本 20.8秒（4本は乱れて再計測が要る）。8バッチでは見えなかった、6本と8本がほぼ同じであることが分かった。1回の調整は検証環境Bで約5分かかる。
- ウォームアップの1回は8バッチ（`SAMPLE`）で行う。GPU の準備が済めばよいので。

- 測り方：読み込みのあと、同時に訳す形で1回ウォームアップてから（時間に含めない）3回測り、中央値を取る。最初の1バッチが返るまでの時間（画面内の目安）と、ばらつき（最大と最小の差÷中央値）も残す。読み込み直した直後の1回目は、まとめて計算する形の GPU の準備が混ざって1〜2割遅いため（同時4本で3.1〜3.5秒、ウォームアップた後は2.7秒）。
- GPU：まず `DEFAULT_PARALLEL` を基準に測り、残る2・3・4・6・8本を重複なく比べる（現在の順は8・2・3・4・6）。8本は既に候補に入っている。ubatch は設定の値を保つ。
- 16本は設定画面で手で選べるが、自動の候補には入れない（`AUTO_PARALLEL_MAX`）。選び方は全体の時間だけで決まり、16本は最初の行を遅らせる（検証環境Aの実際のページで全体 -16%・最初の行 約+70ms、`docs/10`「同時16本」）。GPU に余裕のあるPCで、作者が選ぶ。
- CPU（自動で CPU になったときを含む）：スレッド数（論理コアの半分・全部）×既定の同時実行数・4・1・2本（重複を除く）。既定を8本へ変えると基準も8本になり、現在の4本も比較候補として残る。
- 選び方：既定の同時実行数より、5%と基準の測定のばらつきの大きい方を超えて速いときだけ切り替える。ばらつきで設定が毎回変わらないようにする。
- 8本は全体の時間が短ければ自動選択される。最初のバッチまでの時間は記録するが選択の条件に含めないため、最初の訳の速さを優先する採否は作者が決める（`docs/07`）。
- 読み込めない設定（GPU のメモリー不足など）は飛ばして続ける。途中でやめると、そこまでの結果から選ぶ。
- 測っている間にPCを操作すると、時間が2〜5割延びる（2026-11-09、作者が触っていた1回目は同時4本で4.0〜4.6秒）。

最適化前の実測（2026-11-09、検証環境A：RTX 4060・Core i3-12100、0.8B、PCを操作していないとき）。自前ビルドの採否には `docs/09` の通常版・キャッシュなしの交互計測を使う。

| 同時に訳す同時実行数 | 8バッチ（中央値） | 最初の1バッチ | 生成 | GPU 使用率（3D） | Brave の CPU（PC全体比） |
| --- | --- | --- | --- | --- | --- |
| 1本 | 5.1秒 | — | 約65トークン/秒 | 約33% | 約30% |
| 2本 | 3.3秒 | 0.75秒 | 約100トークン/秒 | — | — |
| 3本 | 2.8秒 | 0.93秒 | 約120トークン/秒 | — | — |
| 4本（既定） | 2.7秒 | 1.07秒 | 約125トークン/秒 | 約35% | 約27% |
| 6本 | 4.0秒 | 3.1秒 | 約84トークン/秒 | — | — |
| 8本 | 3.4〜3.6秒 | 3.5秒 | 約95〜100トークン/秒 | 45〜67% | 約15% |

GPU 使用率はタスクマネージャーと同じカウンター（`\GPU Engine(*)\Utilization Percentage` の 3D）を1秒ごとに取った（ubatch 256〜2048 を同時4本で比べた差は1割以内で、ばらつきの範囲）。

- 当時は GPU 使用率が低いことから、ホストと GPU の往復が主因と見立てた。現在は投入準備、GPU の実行、読み戻し、CPU sampling を分けて確認し、GPU 内の行列計算も短縮する採用パッチが揃った（`docs/09`）。使用率だけでボトルネックを決めない。
- 最適化前に6・8本が遅くなった経路は、matmul の MMVQ 化で改善した。8本は全体の時間と最初の訳までの時間の両方を見て選ぶ。
- ubatch は同時実行数と独立に扱う。8本の採用実測も既定の512で行っており、今回の変更では上げない。
- 結果は `tuneResult` として local に残し、設定画面に表で出す。モデル（0.8B・2B）で合う値が違うので、モデルを替えたら合わせ直す。
- 「今の設定で測る」は同じ測り方（ウォームアップ1回と3回の中央値）を今の設定で行う。結果は「このPCに合わせる」と同じ形（`kind: 'speed'`、行は1つ、選んだ設定なし）で `tuneResult` に残し、設定画面は同じ書き方・同じ表で出す。
- 測るのはモデルの速さだけで、ページの段落の集め方や書き込みは含めない。ページ全体の時間は `tools/bench.mjs` で測る。文章は英語だけなので、ほかの言語で桁が変わることはないが、数%の違いは出うる。

開発用には `tools/tune.mjs` で同じ調整を新しいプロファイルで動かせる。

## PFML3 プロンプト

`shared/prompt.js` の `buildPrompt`。チャットテンプレートを使わず、改行を入れずに1行につなぐ。

```text
<|plamo:tag|>dataset<|plamo:msg|>translation<|plamo:tag|>input[<|plamo:key|>lang<|plamo:val|>{原文の言語}]<|plamo:msg|>{原文}<|plamo:tag|>output<|plamo:key|>lang<|plamo:val|>ja<|plamo:key|>form<|plamo:val|>{polite|plain}<|plamo:msg|>
```

- 温度0（貪欲法）、`<|plamo:tag|>`・`<|plamo:bos|>` で止める。
- 原文の言語は既定で書かず、モデルに判定させる。設定やテキスト翻訳で決めたときだけ書く。
- 訳文の言語は既定で `ja`。テキスト翻訳で日本語以外を選んだときはそのコードを書き、`form`（文体）は書かない（Androidアプリの `Pfml3PromptBuilder` と同じ）。
- 原文に `<|plamo:` が混ざるとプロンプトが壊れるので取り除く。
- 生成の上限は原文の字数の1.5倍＋48（最大1536トークン）。日本語の訳文は原文とほぼ同じ字数かそれより短く、1字はおよそ1トークン以下なので足りる。止まらなくなったときに長く出し続けないよう低めにしている（以前は3倍・最大3072）。

## まとめ訳し

`core/translator.js` の `translateBatch`。ページ側は1段落を1行にして、8行・400字までのバッチで送る（`shared/text.js` の `chunk` と同じ上限）。

1. キャッシュを引き、ある行はそのまま返す。
2. 残りが1行だけ、または1200字を超える段落を含むなら、1行ずつ訳す（長い段落は文の切れ目で分ける。`splitLong`）。分けた片は `translateText` が同時に送り、順番どおりにつなぐ（sakutto の、長い段落の片を空いた同時実行数へ散らす工夫。3片なら約3片分の待ちが約1片分＋αになる見込み、未計測）。片が多いと、選択範囲用に空けた1本も埋まりうる。行数ずれ・訳されていない行の訳し直しは、例外的な経路なので1行ずつ順に送る。
3. 残りを改行でつないで1回で訳し、訳文を改行で分ける。
4. 行数がずれたら、そのバッチを1行ずつ訳し直す（Android の `BatchTranslator.kt` と同じ）。生成を打ち切ったとき（`cut`）も、行数が合っていても同じく1行ずつ訳し直す。行の出しすぎは先頭から送った行数で切るので、モデルが1段落を2行以上に分けて返していると、以降の訳が1段落ずつずれ、最後の段落の訳が抜けたまま行数だけが合うため（2026-11-13、0.8.7）。
5. 行数が合っても、訳されていない行（`untranslated`：原文のまま、または日本語の文字が1つも無い）は、その行だけ1行ずつ訳し直す。言語の混ざったバッチでは、0.8B が最初の言語の行だけ訳して残りを原文のまま写すことがあるため（2026-11-09、韓国語・フランス語・ドイツ語の3行）。
6. ただし、3語以下かつ24字以下の英字の行（製品名・モデル名・ボタン名）は、原文のまま返るのが正しいことが多いので訳し直さない。GitHub Copilot の設定ページでリクエストが70回から53回に減り、全体が56.9秒から50.4秒になった。

テキスト翻訳は `translateLines`：行ごとに分けて同じバッチで訳し、バッチは全件同時に送る（空行は保つ）。送信数を設定の同時実行数にそろえる提案は「同時実行数の切り替えとメモリー」を参照。

## 生成の打ち切り

Offscreen Documentは訳文を少しずつ受け取り（`stream: true`）、`shared/text.js` の `runaway` が止まらなくなったと判断したら中止して、繰り返した部分を捨てる。

- 末尾が同じ並びの3回の繰り返しになった（3回で24字以上のとき）。ただし、訳文が原文の字数の1.2倍＋16字を超えるまでは止めない。原文にもともと繰り返しがある（「min min min…」「Copied Copied…」など）と、正しい訳文も繰り返しになるため（2026-11-09、作者の Brave で正しい訳を打ち切っていた）。
- まとめ訳し（2行以上）で、送った行数より2行以上多く出し始めた。先頭から送った行数で切るが、切った訳文の行と段落の対応は信用せず、バッチを1行ずつ訳し直す（「まとめ訳し」の4）。1段落の訳は行数では切らない。モデルは1段落の訳を複数行に分けて返しうるので、行数で切ると2行目以降の文が黙って抜けるため（2026-11-13、0.8.7）。1段落の生成の長さは生成の上限が抑える。

2026-11-09、GitHub の利用状況のページで、残りの段落が無いのに「訳しています」のまま GPU を使い続けたため入れた。逐次受け取りにしたことで、GitHub Copilot の設定ページの全体の時間が約1割延びた（50.4→56.0秒、画面内は同じ）。

CSS をそのまま長く写し続けるケースは、段落を集める段階で除外して防ぐ（`docs/04`「訳さないもの」）。生成の打ち切りは繰り返しと行の出しすぎを検出する。

## 生成の途中経過

まとめ訳しのときだけ、Offscreen Documentは生成の途中で行が増えるたびに（0.25秒おきまで）`partial` をService Workerへ送る。Service Workerは、そのリクエストでバッチの何行目を訳しているか（キャッシュにあった行は送らないのでずれる。`core/translator.js` の `partialLines`）から、訳し終わった行（最後の行は途中なので除く）を、バッチの行の番号に戻してページへ `show-partial` で渡す。ページは先に書き込み、最後の返事で書き直す。キャッシュには最後の返事だけを入れる。

## 取り消し

ページ側は、送ったバッチの段落がすべてページから消えたか文字が変わったら `cancel` を送る。Service Workerは番号（タブ・枠・バッチ）を取り消し済みにし、Offscreen Documentの生成を止める。まとめ訳しの訳し直しなど、同じ番号で後に続くリクエストも送らない。取り消したバッチは、ページへ `{ cancelled: true }` を返す（失敗ではない）。

## 訳文のキャッシュ

`core/cache.js`。鍵は「モデル｜原文の言語｜訳文の言語｜文体｜原文」。0.10.5 で訳文の言語を足したので、それより前のキャッシュは使われない（訳し直す）。

- 設定画面に、IndexedDB の件数と大きさ（鍵と訳文の字数×2バイトで見積もる）と、拡張機能がブラウザーの中で使っている量の合計（`navigator.storage.estimate`。翻訳モデルを含む）を出す（`cache-stats`）。
- メモリー（3000件）と IndexedDB（最大2万件、古く使ったものから消す）の2段。Service Workerは数十秒使わないと止まり、メモリーのキャッシュはそのたびに消えるので、IndexedDB に残す。書き込みは0.3秒ためてまとめる。
- ページ側は、訳し始め・書き換え・モデルの切り替えのときに、先に `cache-lookup` でキャッシュをまとめて引き、ある分をすぐ置き換える。以前はキャッシュにある文も、生成中の4本の後ろに並んで待っていた。
- 実測：GitHub Copilot の設定ページを読み直した2回目は、323段落を0.1秒（リクエスト0回）で置き換えた。モデルを解放しService Workerを止めた後も、同じ文は7ミリ秒で返った（モデルは読み込まない）。

## メモリーの解放

`background/idle.js`。最後に訳した時刻を `storage.session` に置き（20秒に1回まで書く）、1分おきの見回り（`chrome.alarms`）で、設定の分数（既定10分）を過ぎていたらOffscreen Documentを閉じる。閉じると WASM・WebGPU のメモリーもすべて返る。初回の取得など読み込みの途中は閉じない。ボタンのメニュー・ボタンの右クリック・設定画面から、すぐに閉じることもできる。

## ブラウザー内の速さ

以下は最適化前の調査記録。現在の採用パッチの効果と内訳は `docs/09` を参照する。翻訳サーバー（ネイティブの llama-server）をやめてブラウザー内だけにする前に、試作ページで測った（2026-11-09、「동대문역」の同じバッチ、Brave 157、WebGPU、マルチスレッド有効）。

| | ネイティブ（4本同時） | ブラウザー内（1本） | ブラウザー内（4本同時） |
| --- | --- | --- | --- |
| 0.8B | 約120トークン/秒 | 生成38トークン/秒 | 約47トークン/秒（ネイティブの約0.4倍） |
| 2B | 約28トークン/秒 | 生成21・原文の読み込み58トークン/秒 | 約16トークン/秒（ネイティブの約0.57倍） |

遅くなる箇所（切り分けの結果）：

- 全層と KV キャッシュは WebGPU に載り、CPU のスレッドを1本にしても速さは同じ。CPU 側の処理が原因ではない。
- **原文の読み込み**（まとめた計算）が約6倍遅い。2Bでネイティブ483（行列専用回路なしでも378）に対し、ブラウザー内66トークン/秒。WebGPU 版（ggml-webgpu）の行列計算そのものが遅い。Brave の WebGPU（Windows、D3D12）は `subgroups` まで使えるが、行列専用回路の拡張（`chromium-experimental-subgroup-matrix`）がなく、`--enable-unsafe-webgpu` でも出ない。
- **訳文の生成**は、1トークンごとに約13〜18ミリ秒の固定の上乗せがある（2B：ネイティブ34.5→ブラウザー内47.6ミリ秒、0.8B：8.5→25.6ミリ秒）。GPU への命令の発行と結果の受け取りの手間と見られる。小さいモデルほど比率が悪い。
- Flash Attention は WebGPU 版が KV の行方向に対応しておらず無効になる。明示的に切ると生成が21→11トークン/秒とさらに遅くなる。

見立て：ブラウザー内の0.8Bは、ネイティブの2Bより全体で約1.7倍速い。セットアップなしで使える利点を取り、ブラウザー内だけにした（2026-11-09、作者の判断）。
