# 性能の仮説検証

更新日：2026-11-10

ブラウザー内の 0.8B 翻訳を、計測で説明できる仮説検証で速くした記録。実験ごとに「観測 → 仮説 → 予測 → 変更 → 実測 → 判定」を残す。ビルドと計測の手順は `docs/08_wllamaビルドと計測.md`。数値の検算と、次に試す案の優先順は [高速化の検算と次の案](10_高速化の検算と次の案.md)。

## 計測の条件

ページを読むまでの時間、スクロール後の追従、訳す範囲の比較には [ページ翻訳のUX計測](13_ページ翻訳のUX計測.md) の定義を使う。この節は生成処理の仮説検証の条件を記す。

- 検証環境A：RTX 4060、i3-12100、Brave（新しいプロファイル）。モデルは 0.8B Q4_K_M、語彙 107,520。
- 負荷：`background/tune.js` の8バッチ（各4行の英文）、同時4本、ウォームアップ1回のあと3回の中央値。
- 時間の比較は通常版の交互計測で行う。内訳は計測版（上乗せ約17%）で取り、回数・バイトは計測版でもそのまま比べられる。
- 計測中にほかの重い処理（ビルド・Codex の作業）が動いた結果は、時間の採否に使わない。

## 実験

### E1：GPU への投入準備を減らす（`patches/commands`）

- 予測：事前の数値予測なし（検証の型を整える前に実施。以後の実験では先に予測を書く）。
- 変更：bind group の使い回し、カーネル引数の一括書き込み、重複する queue 待ちの省略（sakutto の 0004 から移植）。
- 実測（計測版、1周）：bind group 作成 56,810→4,643回（340→39ms）、引数の書き込み 58,578→2,914回。
- 判定：仕組みどおりに効いた。時間の採否は E1+E4 で行う。

### E4：logits の読み戻しと CPU の sampling をやめる（`patches/sampling`）

- 予測：事前の数値予測なし（同上）。
- 変更：temperature 0 の翻訳に限り、GPU で選んだ token ID だけを読む（`backend_sampling_token_only`）。WebGPU の argmax の同点規則を CPU にそろえた。
- 実測（計測版、E1 と重ねて1周）：sampling 251→1.3ms、ホストへの読み戻し 151→5.6MB、tensorRead 545→147ms、mapWait 501→124ms。
- 判定：仕組みどおりに効いた。

### E1+E4 の合計

- 実測（通常版）：8バッチ 2.29→1.62〜1.77秒（安定した基準 2.29〜2.30秒に対して -23〜-29%。基準が 3.07秒に乱れた回との比は -42%）。訳は基準でも出る揺れの範囲、マーカーは保持。
- 残った支配項：queueWait 1,050→1,096ms（変わらず）。step 時間 ≈ 7.6 + 1.6×行数（ms）。1行の step が 140 中 50 回で、decode 時間の約28%を使い、トークンの15%しか出していない。

### H1：終わる時刻のずれで1行の step が増えている（支持）

- 観測：上記。Worker の稼働率は約97%（step 間の空き 53ms／1.79秒）なので、JS 側の往復は全体の時間を決めていない。
- 仮説：同時実行数を8にして、5行以上の行列積を MMVQ で流せば（`patches/matmul`）、1 step に乗る同時実行数が増え、step 数が減る。
- 予測：decode step 140→約50、平均同時実行数 2.35→約6.5、decode 時間 1.66→約1.0秒。前提は「step 時間が行数に線形で、8行で約20ms」。同時4本では MMVQ の差は出ない（対照）。
- 変更：E1+E4 に `patches/matmul` を重ね、同時4本と8本で比べた（計測版、`profiles/1794239052688`・`1794239104063`）。
- 実測：

  | 条件 | 8バッチ | 最初の1バッチ | decode step | 平均同時実行数 | decode 時間 | 8行の step |
  | --- | ---: | ---: | ---: | ---: | ---: | ---: |
  | 同時4本、MMVQ なし | 1.87秒 | 0.71秒 | 140 | 2.35 | 1.66秒 | — |
  | 同時4本、MMVQ あり（対照） | 1.87秒 | 0.69秒 | — | — | — | — |
  | 同時8本、MMVQ なし | 2.72秒 | 2.71秒 | 50 | 6.58 | 2.58秒 | queueWait 45ms 相当で遅い |
  | 同時8本、MMVQ あり | 1.18秒 | 1.17秒 | 50 | 6.56 | 1.10秒 | 22.1ms |

- 判定：支持。step 数・平均同時実行数・decode 時間は予測どおり（8行の step は予測 20ms に対し 22.1ms）。対照（同時4本）で差が出ないことも予測どおり。訳の違いは配布物でも観測した2か所の言い回しだけ、マーカーは保持。
- 通常版での確認（交互計測、`profiles/1794239193792`・`1794239282234`）：

  | 条件 | 基準（配布物と同じ版） | 候補（E1+E4+MMVQ） | 差 |
  | --- | ---: | ---: | ---: |
  | 同時4本：8バッチ／最初 | 2.36秒／0.95秒 | 1.69秒／0.67秒 | -28〜-31% |
  | 同時8本：8バッチ／最初 | 3.02秒／3.01秒 | 1.13秒／1.13秒 | -62% |

  現行の拡張（同時4本、2.36秒）と比べると、同時8本の候補は-52%。訳の違いは同時4本の基準で観測した言い回しと同じ（同時8本の基準ではたまたま出なかったため review-required と表示）。
- 稼働率（PDH、2秒ごと、各セッションの読込み・追加試行を含む平均）：GPU の 3D エンジンは、同時8本の候補で約60%、同時4本の候補で約50%、同時4本の基準で約35%。CPU 全体は30〜45%（Brave の最大プロセスは1コア相当の約30%）。GPU が約4割の時間は空いているので、「GPU の中のカーネル効率」と「step の間の GPU の空き」の両方に伸びしろがある。どちらが大きいかは計測版の timestamp で分ける。
- 副作用：最初の1バッチが 0.69→1.17秒に遅くなった。8本が同時に始まり、全員が 22ms の step を共有するため。画面に見えている段落を先に出す体験とぶつかるので、H3 で扱う。

### H3：最初の1バッチの遅れ（支持）

- 観測（計測版、同時8本、`profiles/1794239104063` candidate 第2回）：decode の行数は 820ms で 8→7、952ms で 5、1120ms で 1 に減る。早いバッチ（33トークン）は約0.9秒で生成を終えている。それでも8本すべての最後の結果の受け取り（get_result）は 1203〜1210ms に集まり、最初の1バッチは 1.205秒。最後の decode のあと、0トークンの step が約300回（28ms）続く。
- 仮説：終わった本の結果が、全体の生成が終わるまで返らない（受け渡しの経路で止まっている）。step の時間の問題ではない。
- 予測：受け渡しを直せば、同時8本の最初の1バッチは 1.17→約0.9秒（早いバッチの生成終了の時刻）。8バッチの時間は、末尾の空の step 28ms だけ縮む。
- 原因：wllama の get_result は1回ごとに「1 step 進めてから結果を読む」順で、8本が交代でポーリングする。終わった本の結果は、ほかの本のポーリングが進めた step のあとでしか読まれず、全体が終わるまで返らない。末尾の空の step（約300回）も、終わった本のポーリングが step を回すために出る。
- 変更：`patches/result`（結果を先に読み、空のときだけ1 step 進める）。
- 実測（通常版、同時8本、キャッシュなし、`profiles/1794240259791`）：最初の1バッチ 1.77→1.36秒（-0.41秒）、8バッチ 1.77→1.68秒（-5%、判定幅 5〜6% と同程度）。訳は基準でも出る揺れの範囲、マーカーは保持。
- 判定：支持。予測（キャッシュありの条件で -0.3秒）と向きが合い、キャッシュなしでは prefill が長いぶん、早く終わる本との差が大きく出た。8バッチの時間への効果は誤差の範囲。

## 計測の妥当性の見直し

- 計測の8バッチは毎周同じ文なので、server の prompt キャッシュに当たる。同時8本の候補では、prefill の step が 3〜8 トークンしかない。実際のページでは段落ごとに文が違うので、prefill はこれより重い。
- 影響：同時実行数を増やす H1 の利点は decode の step を減らすことなので向きは変わらないが、prefill の重さで差が縮む可能性がある。
- 測り直し（通常版、`cache_prompt:false`、`profiles/1794239878212`・`1794239959284`）：

  | 条件 | 8バッチ | 最初の1バッチ |
  | --- | ---: | ---: |
  | 現行（基準・同時4本） | 3.03秒 | 1.17秒 |
  | 候補・同時4本 | 2.27秒 | 0.97秒 |
  | 候補・同時8本 | 1.72秒（現行比 -43%） | 1.71秒 |

  キャッシュありの -52% より差は縮むが、H1 の効果は残る。以後の採否は、キャッシュなしの条件で行う。
- prefill の重さ（profile-gpu、`profiles/1794239762425`）：同時8本では、8バッチの prefill は 395トークンの step（host 556ms）と 66トークンの step（129ms）の2回。GPU では、prefill の行列積（`mul_mat_reg_tile_q4_K/q6_K`）が 424ms、prefill の attention（`flash_attn_tile`）が 141ms（32回、1回 4.4ms）。prefill で全トークンに掛ける行列の重みは5.6億個（出力ヘッドと埋め込み表を除く）なので、演算量は約0.52 TFLOP。約0.42秒で計算しており、RTX 4060 の fp32 の約8%。

## 8行の step の内訳（E1+E4+MMVQ、同時8本、profile-gpu）

- step 21.7ms の自己時間：投入準備 3.8ms、その他の wasm 2.3、submit 0.2、GPU 待ち 1.9、読み戻し 13.4（Map の待ちに GPU の実行を含む）。説明率 100%（Scope の木の selfMs の合計）。llama のグラフ構築・ggml のスケジューラーは計測点がまだ値を出していない（0ms、要確認）。
- GPU の実行は 13.0ms/step。内訳は MMVQ 9.9ms（q4_K 0.10ms/回、q6_K 0.19ms/回）、attention 1.5ms、argsort 0.65ms（temperature 0 なのに毎 step 走る）、その他。
- 読み方：CPU の準備（約6ms）が終わってから GPU が約13ms 動く直列になっている。GPU の稼働率約60%と合う。

### H7：CPU の準備と GPU の実行が重なっていない（棄却）

- 前提の確認：ggml-webgpu は、すでに64カーネルごとに途中で submit している（8行の step で submit 13回、Map 2回）。「全部 encode してから一度に submit」という前提が成り立たない。
- 計測の読み違い：読み戻しの 13.4ms のうち 12.9ms は、profile-gpu だけが行う timestamp の読み戻しだった。token ID の読み戻しは 0.43ms、32バイト/step。profile-gpu の host 時間の内訳は、通常版の内訳として使えない（以後は profile 版で CPU の内訳、profile-gpu 版で GPU の内訳と分けて取る）。
- 判定：棄却。パッチは作らない。

### H8：8行の MMVQ が重みを読み直している（予測は外れ）

- 前提の確認（コード）：8行の MMVQ は、4列ずつの workgroup を2組起動し、重みを2回読む。行数別の1回あたりの時間は、q4_K で 1行 0.029ms、4行 0.079ms、8行 0.144ms。
- 変更：Q4_K・Q6_K を8列まとめて重みを1回だけ読む（`patches/matmul-h8`、分けて保管）。
- 予測：8行の MMVQ 9.9→約3.5ms、8バッチは短くなる。
- 実測（通常版、同時8本、キャッシュなし、`profiles/1794240769263`）：8バッチ 1.68→1.80秒（+7%、判定幅 5%）、最初の1バッチ 1.38→1.49秒。
- 判定：予測は外れた。重みの読み直しを減らしても速くならず、遅くなった。
- 見直した仮説（H8'）：8列化で1 invocation の主要配列のレジスタ相当量が2倍（q4_K 40→80、q6_K 36→72）になり、同時に動く workgroup が減ってメモリーの待ちを隠せなくなった。8列のときだけ workgroup を256→128にすれば（`matmul-h8/0003`）、0002 比で MMVQ が約3〜16%短くなる。
- 実測（profile-gpu、同時8本、キャッシュなし、第2回、`profiles/1794241848177`）：

  | 版 | 8行の MMVQ/step | 8行の GPU/step | 1行の MMVQ/step | 8バッチ（計測版） |
  | --- | ---: | ---: | ---: | ---: |
  | 基準（matmul 0001） | 11.35ms | 15.2ms | 2.8ms | 1.72〜1.76秒 |
  | 0002（8列、WG256） | 14.1ms | 18.1ms | 2.5〜2.9ms | 1.83〜1.87秒 |
  | 0002+0003（8列、WG128） | 7.94ms | 11.8ms | 2.8ms | 1.59秒 |

- 判定：H8' は支持（0002 比 -44% は予測の 3〜16% より大きい。レジスタの圧迫の影響を小さく見積もっていた）。基準比で 8行の MMVQ -30%。
- 通常版（採用分＋H4＋H6 に重ねる、同時8本、キャッシュなし、`profiles/1794242143890`）：8バッチ 1.526〜1.530→1.393秒（-8.8%、判定幅5%）、最初 1.22〜1.25→1.13秒。訳の違いは2か所の言い回し（「取りこぼし→紛失」は H1 の計測でも同じ揺れを観測）、マーカーは保持。採用する。

### H5（再）：attention のタイル飛ばしの改訂版も読み込み直後に落ちる

- 改訂版（`baseline-candidate-f5f7ff65e7c1`、`profiles/1794242199222`）も `ggml_abort`（WebGPU の未捕捉エラー経由）。計測の道具が Worker のコンソールを残していなかったので、`profile.mjs --native-log`（Worker の Runtime・Log を記録）を足して取り直した。
- 原因：WGSL のパースで `bitcast<f32>(0xff800000u)` が定数として評価され、「value -inf cannot be represented as 'f32'」で shader の作成が失敗していた。mask は `array<f16>` なので、f16 の生ビットを 0xfc00 と整数で比べる判定に直した（f16 の全65,536ビット列で、負の無限大だけを飛ばすことを確認）。
- 実測（採用分＋H8 に重ねる、同時8本、キャッシュなし）：

  | 指標 | 基準 | H5 | 予測 |
  | --- | ---: | ---: | --- |
  | prefill の attention（`flash_attn_tile`、32回） | 106〜113ms | 22〜23ms（約0.7ms/回） | 約0.8〜1.7ms/回 |
  | prefill の GPU 合計 | 427〜449ms | 336〜359ms | — |
  | 8バッチ（通常版、`profiles/1794243213555`） | 1.337〜1.366秒 | 1.277秒（-4.5〜-6.5%、判定幅 5〜6%） | 約-0.1秒 |
  | 8バッチ（profile-gpu、`profiles/1794243439250`） | 1.417〜1.423秒 | 1.278秒（-10%） | — |

- 判定：支持。カーネルの時間は予測より少し大きく減り、prefill の GPU は約80ms 減った。通常版の全体の差は判定幅と同程度だが、仕組みが GPU 時間で確かめられたので採用する。訳は基準でも出る揺れの範囲、マーカーは保持。

### H4b：prefill で行列演算器（subgroup matrix）を使う（保留）

- 確認（`tools/wllama/patches/prefill-matrix/probe.mjs`、RTX 4060、普段の Brave、新しいプロファイル）：adapter は `shader-f16`・`subgroups`（幅32）を出すが、`chromium-experimental-subgroup-matrix` を出さない。更新候補の emdawn には API がある。
- 判定：配布する拡張の普段の起動条件では使えないので保留。Brave が標準で公開したら、版の更新案（`prefill-matrix/pins.diff`、Dawn v20260818.211311）から再開する。

## 最終の通算（同梱した版と現行の比較）

同梱した版：7フォルダー12パッチ（commands、sampling、matmul、result、prefill、matmul-h8、attn、`baseline-candidate-b68ace09e1fe`）＋ offscreen の `backend_sampling`・`backend_sampling_token_only`・`samplers:["temperature"]`。現行は配布物と同じ版で、offscreen の設定を元に戻して測った（`backend_sampling:false`・`samplers:null`）。通常版、キャッシュなし、交互計測（`profiles/1794243851243`・`1794243924652`）。

| 条件 | 8バッチ | 最初の1バッチ |
| --- | ---: | ---: |
| 現行（同時4本） | 2.94秒 | 1.18〜1.21秒 |
| 同梱した版・同時4本 | 1.98秒（-33%） | 0.75秒（-37%） |
| 同梱した版・同時8本 | 1.24秒（現行比 -58%） | 0.99秒（現行比 -17%） |

訳の違いは、基準でも観測した3か所の言い回しだけ。マーカーは保持。通しの試験 26/26 合格（CPU の4スレッドの翻訳を含む）。

## GPU の使用率が上がらない理由（考察、2026-11-10）

作者の観察：0.7.0 で出力の速さは確実に上がったが、タスクマネージャーの GPU 使用率はむしろ下がった。効率は良くなったが、GPU を使い切れていない。

計測（profile-gpu、同時8本、各 step の GPU timestamp の合計と host の時間）：

| 版 | decode 8行の step（GPU / host） | 1行の step（GPU / host） | 第2回全体の GPU 合計 / 経過 |
| --- | ---: | ---: | ---: |
| E1+E4+MMVQ（`profiles/1794239762425`、キャッシュあり） | 15.5 / 22.3ms（69%） | 4.6 / 14.4ms（32%） | 683 / 1,220ms（56%） |
| 最終（`profiles/1794243439250` candidate、キャッシュなし） | 10.6 / 16.3ms（65%） | 4.3 / 10.4ms（41%、定常の step。行数が変わった直後の step を含む平均は 4.4 / 12.9ms） | 806 / 1,271ms（63%、prefill が重いぶん高い） |

読み方：

1. **GPU の仕事を減らしたが、step ごとの CPU の固定費は減っていない。** 8行の step の「host − GPU」は 6.8→5.7ms とほぼ同じで、GPU の時間だけが 15.5→10.6ms に縮んだ。step は「CPU が計算グラフを組んで投入 → GPU が計算 → token を読む」の直列なので、使用率 ≒ GPU ÷（GPU ＋ CPU の固定費）が下がる。速くなった分だけ、GPU が待つ時間の割合が増えた。
2. **CPU の固定費は token の依存では説明できない部分が大きい。** 次の token の入力は前の step の結果に依存するが、計算グラフの形と bind group・投入準備の大半は token の値に依存しない。8行の step の CPU 側 約6ms は、H9 を立てた時点の版では投入準備（webgpuPrepare）約3.8ms とそのほかの wasm 約2ms だった。最終版（0.7.0）では、投入準備 2.20ms、スケジューラー 1.12ms、グラフ構築 0.02ms（使い回しが効いている）、そのほか 0.57ms、待ちの上乗せ 1.86ms（`docs/10`「検証環境Aの時間の内訳」）。
3. **実際のページでは1行の step が多い。** ページの翻訳はバッチが少しずつ届き、終わりかけでは行数が減る。定常の1行の step の GPU の割合は約41%（GPU 4.3ms に対し CPU 側 約6.1ms）。CPU 側は行数によらず5〜6ms なので、行数が少ないほど割合が下がる。さらに、バッチが終わるたびに次の step が約10ms 遅くなる（`docs/10` の N1）。8バッチの試験より、実際のページのほうが使用率は低く出る。
4. **タスクマネージャーの値の性質。** `GPU Engine 3D` の使用率は「GPU にコマンドが載っている時間の割合」で、演算器の埋まり具合ではない。GPU の中の効率（行列・ベクトル積は重みを読む下限の約3〜4倍、prefill の行列積は fp32 の約11%）は別に見る。

次の仮説の候補（未検証、数値はこの計測からの見積もり）：

| 候補 | 狙う指標（いまの値） | 変更 | 予測 |
| --- | --- | --- | --- |
| H9 step ごとの固定費 | 8行の step の CPU 側 約5.7ms、1行 約6.1ms | グラフの使い回しは既に効いており、WebGPU のコマンドは使い回せない。残りは `docs/10` の N2（待ちの回数）・N3（CPU と GPU の並行）・N4（GPU の中で数トークン進める）に分けた | CPU 側を半分にできれば 8行 16.3→約13.5ms、1行 10.4→約7.4ms。GPU の割合 65%→約78% |
| H10 計測点の欠け（完了） | llamaGraph・backendScheduler が 0ms | 最終版の profile-gpu では値が出ている | 8行の step の内訳は説明率100%（`docs/10`） |
| H11 行列・ベクトル積の帯域効率 | 8行で 7.9ms、重みを読む下限 約2ms | 量子化ブロックの読み方・ベクトル化の見直し | 下限の2倍（約4ms）まで縮めば 8行の step -4ms |
| H12 prefill の行列積 | 300ms（fp32 の約11%） | subgroup（行列演算器なし）を使うタイル、または Brave が subgroup matrix を出すのを待つ | 未見積もり |

検証環境B（Radeon 860M、内蔵GPU、メモリー帯域はCPUと共有）では、GPU が RTX 4060 より遅いぶん GPU の割合が高く出る見込み。一方、メモリーの帯域を CPU と分け合うので、H11 の効き方は違う。まず同じ計測で、この表の数字を検証環境Bで取る（引き継ぎは `docs/00`「次の作業」）。

## 同時実行数の上限（検証環境B、2026-11-10）

作者の観察：検証環境Bのブラウザーで試すと8本が最適だったが、まだ頭打ちに見えないので、もっと同時実行数を上げた所に最高性能があるのではないか。

問題点：「このPCに合わせる」と `profile.mjs` の計測対象は8バッチ固定。8本で一度に流し切れ、6本は6＋2の2巡になる。8本を超える同時実行数は試せない。そこで `tools/parallel-sweep.mjs` で、`SAMPLE` の行を組み替えた32バッチ（文章量は4倍、すべて別の文）を測った。

| 8・8本 | 3.93秒 | 3.23秒 | 85.7 | 73% | 31% |

4. **24本は遅くなる。** GPU 3D は91%と最も高いが、全体は8本より約35%遅い。同時実行数に比例して KV（文脈長 4096×(同時実行数＋1)）と attention が重くなる仮説があるが、未検証。

## sakutto との比較と取り込める案（2026-11-10）

同じ PLaMo＋wllama の拡張機能 sakutto（`jammaru/sakutto`、MIT）を、前回取り込んだ `73ed047` から `dc6a500`（2026-11-10）まで読み直した。73ed047 以降の速さに関わる変更は、AMD・Intel の GPU で CPU へ落ちる不具合の修正（#49、パッチ0007・0008）だけで、ほかは Firefox 対応・ショートカット・文書。速さの主な変更（#22 の同時2本、#27 の同時16本）は前回までに読んでいる。

### 方針の差

sakutto は「GPU カーネルには手を入れず、同時に流す同時実行数とページの組み立てで稼ぐ」。この拡張は「同時実行数は PC ごとに測って選び、GPU カーネルと step の固定費を計測で削る」。sakutto の 0004（bind group の再利用・MMVQ の複数列）は、この拡張の commands・matmul の元になった。

| 観点 | sakutto（dc6a500） | この拡張（0.7.0） |
| --- | --- | --- |
| 同時実行数 | NVIDIA かつ整数の内積（dot product）を持つ GPU だけ16本、ほかは4本。読み込み失敗・GPU の消失で 16→4→1→CPU と段階的に下げる | 既定8本。「このPCに合わせる」で測って選ぶ。GPU で読めなければ CPU |
| 1本あたりの文脈 | 1024 トークン（16本で 16,384） | 4096 トークン（スロットは同時実行数＋1なので、8本で 36,864） |

### GPU の内訳（基準、profile-gpu、`profiles/1794232524570`）

- GPU 時間の74%は行列・ベクトル積（q4_K 363ms・7,008回、q6_K 272ms・2,482回）。attention 111ms、norm 62ms。1 step のカーネル数は389。
- 1行の step の GPU 4.1ms は、1 step に読む重み 477MB（埋め込み表を除く）に対して約116GB/s で、RTX 4060 の上限（約272GB/s）の約43%。行列・ベクトル積のカーネル効率に伸びしろがある（次の仮説の材料）。
- 注意：profile-gpu は計測のために同期を足すので、その host 時間は通常版と比べない。

### H2：1 step の固定費は GPU の実行ではなく投入の待ち（棄却の見込み）

- 観測：1行の queueWait 5.2ms に対し、GPU の実行時間は 4.1ms。重みを読む下限は約1.8ms（477MB／272GB/s）。
- 判定（暫定）：queueWait の大半は GPU の実行。固定費の主因は「投入の待ち」ではなく、GPU 側のカーネルの効率（下限の約2.3倍）。カーネル別の内訳で次の仮説を立てる。
