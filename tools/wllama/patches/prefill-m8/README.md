# Q4_K/Q6_K の prefill で1スレッドの受け持ちを 8×8 にする

`0001-widen-kquant-thread-tile.patch` は、`prefill` の `0001`（出力タイル 32×64、K 方向 64）の上に当てる。Q4_K/Q6_K の `mul_mat_reg_tile` で、1スレッドが受け持つ出力を 4行×8列から 8行×8列へ広げる（`TILE_M` 4→8、pipeline 名に `_m8`）。

## 仮説と予測

実際のページの読み込み（prefill）の GPU 時間の86%がこの行列積で、時間は読み込むトークン数にほぼ比例していた（Q4_K で 2.72ms/トークン。`docs/10`「実際のページの時間と GPU の内訳」）。重みの展開は workgroup ごとに1回なので主因ではない。内側のループは、積和32回ごとに共有メモリーを12回（行4＋列8）読む。読み出しが律速なら、8×8にすると積和64回ごとに16回となり、積和1回あたりの読み出しが約1/3減る。

同時に試した「共有メモリーの f16 を f32 へ直すのを取り出し時の1回にまとめる」案は、行列積の時間が -1% で効かなかった（コンパイラーが既にまとめていたと見られる）。採らない。

## 選択条件

Q4_K/Q6_K、subgroup matrix なし、`prefill` の条件（共有メモリー上限 12288 バイト以上）に加え、上限 16384 バイト以上のとき。共有メモリーは 16KB で、WebGPU がすべての device に保証する上限（16384 バイト）に収まる。GPU 名では分けない。accumulator は 1スレッド 32→64 要素に増えるので、レジスターの少ない GPU で遅くならないかは、ほかの GPU でも確かめる。

## 結果（2026-11-10、検証環境B：Radeon 860M、同時8本）

| 計測 | 基準 | 8×8 | 差 |
| --- | --- | --- | --- |
| 実際のページ、profile-gpu の mixed step の Q4_K 行列積 | 4,559ms（705回） | 3,497ms | -23% |
| 同、Q6_K 行列積 | 1,032ms | 815ms | -21% |
| 8バッチ（通常版、前後の基準と） | 3.995・4.180秒 | 3.672秒 | -8.1%・-12.1%（判定幅 7.3%） |

訳の違いは基準どうしでも出る揺れの範囲で、マーカーも保った（`profile.mjs`、quality-replays 2）。読み出しを約1/3減らして行列積が約2割縮んだので、読み出しは原因の一部であって全部ではない。特別な命令なしのネイティブ（読み込み全体で約0.7ms/トークン）までは、行列積だけ（約2.5ms/トークン）でもまだ約3.5倍ある。

実際のページ（MDN の GPUAdapter、同時8本、通常版を交互3回）では 42.3・38.6・43.0秒 → 36.4・41.3・39.0秒（中央値 -7.8%）。PC 全体が普段の約2.5倍遅い状態での相対値。3つの計測の向きがそろったので、2026-11-10 に同梱した（`baseline-candidate-79a95eddee83`）。NVIDIA など他の GPU で遅くならないかは、次にそのPCで測るときに確かめる。
